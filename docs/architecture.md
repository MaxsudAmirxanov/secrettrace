# SecretTrace — архитектура

Защитный инструмент класса secrets governance / DLP / honeytokens. Работает только в инфраструктуре владельца:
секреты регистрируются по отпечатку, сканеры находят, куда они попали, коллекторы — кто ими пользуется.

## 1. Отпечатки: как найти секрет, не храня его

```
клиент (браузер / CLI / агент)                       сервер
canonical = normalize(type, value)
d = SHA-256("secrettrace/v1\0" || canonical)  ──mTLS──▶  fp = HMAC-SHA256(pepper_v, "secrettrace/fp/v1\0" || d)
                                                          lookup (pepper_version, fp) в secrets
```

- **Открытое значение не покидает клиента.** Регистрация идёт через `secrettrace digest` или WebCrypto в браузере.
- **Pepper есть только на сервере** (Docker secret / env; позже Vault Transit). Дамп БД без pepper бесполезен для перебора.
  Pepper не раздаётся агентам: иначе взлом любого хоста вместе с дампом БД дал бы офлайн-перебор слабых паролей.
- **Остаточный риск:** digest слабого пароля можно подобрать. Поэтому transport только TLS/mTLS, тела `/ingest` не
  логируются, на `/ingest/match` стоят rate-limit и аудит (иначе это оракул «зарегистрирован ли пароль X»).
- **Версии pepper.** Пересчитать старые отпечатки без значения нельзя, поэтому новые секреты получают текущую версию,
  а матчинг проверяет все настроенные версии. Старая версия уходит вместе с ротацией самих секретов.
- **Нормализация** (`st-core::normalize`): trim; PEM сводится к base64-телу (переносы, `\r\n` и экранированные `\n`
  не важны); публичный ключ OpenSSH — к blob'у; многострочные значения разрешены только для ключевого материала.
- **Политика hints** (`st-core::hints`): префикс хранится, только если это публичный вендорский префикс из списка
  (`AKIA`, `ghp_`, `sk_live_`…), длина — только вместе с ним, суффикс из 4 символов — только при длине ≥ 24.
  У паролей и строк подключения подсказок нет никогда; это дополнительно гарантирует CHECK в БД.
- **Двухфазный ingest.** `/match` получает дедуплицированные digest'ы и возвращает совпавшие, `/findings` получает
  расположения только для совпадений. Сервер перепроверяет digest и не доверяет клиенту.

## 2. Компоненты

```
            ┌──────────── nginx (edge, этап 13) ───┐
 браузер ──▶│ :443  TLS → web (static) + /api      │
 агент/CI ─▶│ :8443 mTLS → /api/v1/ingest          │
            └───────────────┬──────────────────────┘
                            ▼
      secrettrace-server serve  ◀── Postgres 17 ──▶  secrettrace-server worker (этап 9)
      (axum)                       реестр, locations,  очередь SKIP LOCKED, outbox алертов,
                                   алерты, аудит       cron истечения сроков
```

| Крейт | Назначение |
|---|---|
| `st-core` | нормализация, digest, hints, маскирование; без сети и без pepper |
| `st-extract` | извлечение кандидатов из текста, локальный digest; общий для CLI, агентов и воркера |
| `st-source` | источники: файловая система и git-история → документы для экстрактора; пул потоков |
| `st-server` | API, воркер, админ-команды (`migrate`, `verify-audit`, `gen-pepper`) |
| `st-cli` | `secrettrace`: `digest`, `extract`, `scan fs|git` (локально); `register` и отправка на сервер позже |

Очередь в MVP — сам Postgres (`FOR UPDATE SKIP LOCKED` + outbox). NATS JetStream появится на этапе 2 для
потоковых коллекторов. События использования будут лежать в партиционированной таблице (TimescaleDB при росте).

## 3. Безопасность самой системы

- Две роли БД: `st_owner` (только миграции) и `st_app` (рантайм). У `st_app` отозваны `UPDATE/DELETE/TRUNCATE`
  на `audit_log` и доступ к `_sqlx_migrations`. Это проверяется тестом.
- Журнал аудита — hash-chain: `hash = SHA-256(domain || prev_hash || length-prefixed поля)`, вставки сериализованы
  advisory-lock'ом в транзакции действия. `secrettrace-server verify-audit` пересчитывает всю цепочку.
  Ограничение: удаление хвоста цепочки не обнаруживается; планируется периодический экспорт head-хеша.
- Секреты в коде типизированы: `SecretString`, `Zeroizing`, `Digest`/`Fingerprint` с урезанным `Debug`.
  HTTP-трейсинг пишет только метод и путь, без query и заголовков. Ошибки — RFC 7807 без внутренних деталей.
- Контейнеры: distroless nonroot, read-only FS, `cap_drop: ALL`, `no-new-privileges`, все секреты — Docker secrets.
- CI: rustfmt, clippy pedantic с `-D warnings`, тесты на Postgres, `cargo audit`, gitleaks по всей истории.

## 4. Авторизация

- **Пароли:** argon2id (m=19 МиБ, t=2, p=1), минимум 12 символов, максимум 256 байт. Для несуществующих
  пользователей хеш всё равно вычисляется, чтобы по времени ответа нельзя было узнать, есть ли учётная запись.
- **Вход в два шага:** пароль даёт pre-MFA сессию на 5 минут, TOTP (RFC 6238, SHA1/30 с/6 цифр, допуск ±1 шаг)
  даёт новую сессию: токен меняется, это защита от session fixation. MFA обязательна для всех ролей.
  Первая привязка TOTP происходит при первом входе; повторная — только после `reset-mfa` администратором.
- **TOTP seed** хранится зашифрованным AES-256-GCM (`ST_DATA_KEY`), id пользователя служит associated data.
  Номер последнего принятого шага (`totp_last_step`) запрещает повторное использование кода.
- **Сессии:** в cookie лежит случайный токен (256 бит), в БД — его SHA-256. Cookie `HttpOnly; SameSite=Strict`,
  в production `Secure` и префикс `__Host-`. Абсолютный срок жизни 12 ч, тайм-аут бездействия 30 мин.
- **CSRF:** `X-CSRF-Token = base64url(SHA-256(domain || session_token))`. Токен вычисляется из cookie и нигде
  не хранится; обязателен для всех методов, кроме GET/HEAD/OPTIONS.
- **Перебор:** 5 неудачных попыток (пароль или TOTP) блокируют учётную запись на 15 минут; активная блокировка
  не продлевается, чтобы атакующий не мог держать её вечно. Дополнительно in-process лимиты: 20 входов
  в минуту с IP, 10 на имя пользователя, 5 проверок TOTP. Все неудачи дают одинаковый 401, причина — в аудите.
  Введённое имя несуществующего пользователя в аудит не пишется: туда часто по ошибке вводят пароль.
- **Роли:** `viewer < operator < admin`, проверка `CurrentUser::require(role)` в каждом обработчике.
- **API-токены** (`stk_<id>_<секрет>`) только для машин: scopes `ingest:*`, обязательный срок жизни
  (до 365 дней), хранится SHA-256, отзыв действует сразу. Привязка к CN клиентского сертификата mTLS — этап 13.
- **IP клиента** берётся из адреса соединения; `X-Forwarded-For` учитывается только от `ST_TRUSTED_PROXIES`.

## 5. Реестр

- Регистрация принимает только digest. Сервер вычисляет отпечаток текущей версией pepper; дубликат ищется
  по отпечаткам всех настроенных версий (`UNNEST` по парам версия/отпечаток).
- Hints повторно проверяются на сервере (`st_core::validate_hints`); БД дополнительно запрещает их CHECK'ами.
- Allow-rules проверяются при сохранении (`policy::Glob`: линейный DP без регулярных выражений и без
  экспоненциального перебора). Сопоставление найденных мест с правилами выполняется на этапе 8.
- Списки используют курсорную пагинацию по `(created_at, id)`: стабильно при вставках, без OFFSET.
- Аудит: `secret.create`, `secret.update`, `secret.revoke`, `secret.rotate`, `secret.status_change`;
  в деталях — имя, тип, маска и список изменённых полей, без digest и отпечатков.
- Экстракторы `ApiJson` / `ApiQuery` / `ApiPath` превращают любые ошибки разбора в problem+json:
  400 — синтаксис, 415 — тип содержимого, 422 — схема, 413 — размер.

## 6. Извлечение кандидатов

Матчинг идёт по точному равенству digest, поэтому задача экстрактора — полнота, а не точность: лишний кандидат
стоит одного SHA-256 и места в запросе `/match`. Точность выражена отдельно, полем `confidence`. Оно понадобится
для отчётов о незарегистрированных секретах.

- **Конвейер** (`st_extract::Extractor::extract`): известные форматы → PEM/SSH → URL userinfo → key=value
  (присваивания, флаги, XML, `.netrc`, `Authorization`) → экранированные JSON-строки → энтропия и base64.
  Каждое найденное значение проходит `st_core::normalize` для своего типа, затем вычисляется digest.
  Открытый текст живёт только в `Zeroizing`-буферах и в `Candidate` не попадает.
- **Дедупликация.** Если одно и то же значение найдено в перекрывающихся местах, остаётся первый детектор
  по приоритету. Поэтому `ghp_…` внутри `Authorization: Bearer` помечается как `known/github_token`.
- **Рекурсия.** Декодированный текст сканируется как отдельный документ с `Frame`, который отображает
  смещения на внешний фрагмент. Глубина ограничена 3, объём декодирования — `max(4 × вход, 1 МиБ)`.
- **Границы токенов** проверяются вручную, потому что в `regex` нет look-around: `xAKIA…` и токен длиннее
  формата отбрасываются.
- **Отказ от регулярок с backtracking** гарантирует линейное время. Отдельно разобраны квадратичные
  сценарии: поиск `END` для каждого `BEGIN` и сканирование хвоста значения ограничены окном.
- **Вывод CLI** не содержит digest без явного флага: digest слабого пароля перебирается офлайн.

## 7. Источники

Источник отдаёт `Document { locator, text: Zeroizing<String>, encoding, truncated }` в callback, `st_source::scan`
раздаёт документы пулу потоков через ограниченный канал (обход не убегает вперёд извлечения) и собирает
`DocumentFindings` в порядке источника. Результат не зависит от числа потоков. Пропуски считаются в `Stats`,
а не теряются; ошибки чтения хранят путь и ошибку ОС, без содержимого.

- **Файловая система.** `walkdir` без следования по ссылкам и `open(O_NOFOLLOW | O_NONBLOCK)` с `fstat`
  после открытия: симлинк, подменённый после обхода, или FIFO не будут прочитаны. Корень канонизируется,
  поэтому явно заданный симлинк-корень работает. Исключения — glob'ы в духе gitignore; `.git`, `.hg`
  и `.svn` исключены по умолчанию, историю сканирует git-источник.
- **Git: скан.** `rev-list --objects <revs>` → `cat-file --batch-check` (тип, размер, путь) →
  `cat-file --batch` по одному blob'у с синхронным запросом-ответом, поэтому взаимной блокировки на пайпах
  нет. Каждый уникальный blob читается один раз. `--missing=print` и `GIT_NO_LAZY_FETCH` дают shallow
  и partial clone без сетевых запросов; отсутствующие объекты считаются.
- **Git: где лежит.** `locate(blobs)` — один `git log --raw -z --find-object=…` на пачку из 500 blob'ов,
  `--topo-order --reverse`: родители раньше потомков даже при одинаковом времени коммитов.
  `head_blobs()` (`ls-tree -r HEAD`) отвечает на вопрос, есть ли blob в текущем состоянии, это поле
  `locations.in_current_state`.
- **Инкрементальность.** Ревизии `main ^<последний просканированный коммит>` дают только новые blob'ы:
  то, что достижимо из старого коммита, `rev-list` не выдаёт. Воркер этапа 9 будет хранить этот коммит
  в `sources.config`.
- **Изоляция git.** Удаляются унаследованные `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`,
  `GIT_OBJECT_DIRECTORY` и т.п.; `GIT_NO_REPLACE_OBJECTS=1` (иначе `refs/replace/*` скрыли бы настоящее
  содержимое); `GIT_TERMINAL_PROMPT=0`; `log.showSignature=false` (без gpg); `core.fsmonitor=false`.
  Ревизии валидируются и идут после `--end-of-options`. Бинарный образ сервера сейчас distroless и без
  git; для серверного клонирования (этап 9) воркеру понадобится образ с git.
- **Память.** Буферы файлов и blob'ов выделяются один раз точного размера (рост `Vec` оставил бы
  незатёртую копию), декодирование в текст переносит буфер без копирования, буфер чтения из `cat-file`
  затирается. Сам процесс git и ядро (pipe) держат копии, которые мы контролировать не можем.

## 8. Ingest

Четыре вызова на скан: `scans` (старт) → `match` → `findings` → `complete`, все только по API-токену
со своим scope. Каждый обработчик — одна транзакция вместе с записью аудита; строка `scan_jobs`
блокируется `FOR UPDATE`, поэтому параллельные `findings` и `complete` одного скана сериализуются.

- **Скан** принадлежит токену (`scan_jobs.api_token_id`); чужой или несуществующий id дают одинаковый 404.
  Работать со сканом можно, пока он `running` и моложе 24 часов, иначе 409.
- **Матчинг.** Для каждого уникального digest'а вычисляются отпечатки всех версий pepper, затем один запрос
  `UNNEST(idx, version, fp) JOIN secrets`. Статус секрета не важен.
- **Лимиты.** `/match` и `/findings` делят взвешенный бюджет (`RateLimiter::check_n`): уникальные digest'ы
  в час на токен (`ST_INGEST_DIGESTS_PER_HOUR`) и запросы в минуту; иначе `/findings` стал бы оракулом
  в обход лимита `/match`. Старты сканов — 30 в минуту на токен. Отказ не расходует бюджет, проверка скана
  идёт до лимитера. Окно фиксированное (на стыке окон возможен двойной бюджет), лимитер живёт в процессе:
  при нескольких репликах лимит умножается на их число.
- **Проверка URI** отвергает userinfo после любой смеси `/` и `\` за `scheme:`, `user:pass@` без схемы
  и параметры query/fragment с именами вроде `token`, `password`, `key`, `signature`.
- **Ошибки 422** не возвращают присланное: значения и неизвестные имена полей в сообщениях serde заменяются
  на `…` (`extract::redact_input`).
- **Блокировки.** `/findings` берёт `FOR SHARE` на совпавшие секреты до чтения allow-правил (гонка с заменой
  правил), находки сортируются по `(secret_id, locator_key)`, `reevaluate` блокирует места `ORDER BY id`.
  Лимит тела у `/findings` — `max(ST_MAX_BODY_BYTES, 8 МиБ)`, чтобы помещались 5000 находок.
- **Идентичность места.** `locator_key = SHA-256("secrettrace/location/v1\0" || lp(source_type) || lp(uri) ||
  lp(path))`, `lp` — длина 4 байта big-endian и байты. Дубликаты в одном запросе сливаются до `INSERT`,
  потому что `ON CONFLICT` не может обновить одну строку дважды. Новые и обновлённые места различаются
  через `RETURNING (xmax = 0)`.
- **`in_current_state`.** Внутри одного скана — OR по всем находкам пути; находка из нового скана заменяет
  значение. `locator` берётся от версии из текущего состояния. Успешный полный скан снимает флаг с мест
  источника, которых он не видел (`no_longer_present`), но только с тех, что раньше сообщал тот же токен
  и что старше начала скана (`last_seen < started_at`). Скан старше 24 часов можно лишь завершить как `failed`.
- **Известное ограничение:** токен сам выбирает `environment` скана и может подогнать его под allow-правило.
  Закрывается привязкой токена к источнику на этапе 13.
- **Allow-правила** (`policy::allow`): все заданные поля правила должны совпасть, побеждает правило
  с меньшим id. При замене правил `policy::reevaluate` пересчитывает места секрета в той же транзакции:
  удаление старых правил обнуляет `allow_rule_id` через `ON DELETE SET NULL`, но `is_allowed` пересчитать
  может только код.
- **Аудит**: `ingest.scan_start`, `ingest.match`, `ingest.findings`, `ingest.scan_complete` от имени токена;
  в деталях только счётчики и id. Алерты на новые нарушения — этап 10.

## 9. Ошибки API

`application/problem+json`, поле `type` — стабильный URN: `urn:secrettrace:problem:{bad-request|unauthorized|
forbidden|not-found|conflict|validation|rate-limited|payload-too-large|unsupported-media-type|unavailable|internal}`. Корреляция — заголовок `x-request-id`.
